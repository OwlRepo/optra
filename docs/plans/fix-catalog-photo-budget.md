# Fix B7 — catalog photo fetching stays inside the parse attempt

Owner instruction 2026-10-02: continue through the bug list without waiting; pull the owner in only when a decision is needed.

- Classification: BUG_FIX · Deep (Bull catalog-parse processor) · Vendor Catalog / Vision Matching · Jobs. Contract areas: API — none; DB — none; Jobs — the attempt now always ends inside `PARSE_JOB_TIMEOUT_MS`.
- Root cause: `CatalogParseProcessor.parseSpreadsheet` awaited `CatalogImageService.fetchAndStore` once per row, sequentially; each fetch may take up to `IMAGE_FETCH_TIMEOUT_MS` (20 s). With 16+ photos on a hanging host the attempt exceeded the 5-minute Bull `timeout`; Bull 4's `pTimeout` rejects the job promise without stopping the handler, so the retry ran beside the first attempt and both ran the non-transactional `replaceItems`.
- Fix: photos are fetched through `createLimit(4)` and none is started after a 3-minute budget (`PHOTO_PHASE_BUDGET_MS`); a skipped photo is stored as `null`, the same outcome as a failed fetch, and the skipped count is logged. Worst case: 3 min + one in-flight 20 s fetch, inside the 5-minute attempt.
- Not changed (residual, recorded): `replaceItems` stays delete-then-insert outside a transaction. With every attempt bounded below its timeout, two attempts can no longer overlap, which was the only path to interleaving. Making it transactional is a separate hardening change.
- Not changed (product decision, not taken here): telling the user that some photos were skipped. Catalogs have no field for it; it would need a schema or UI change.
- Tests first (`catalog-parse.processor.spec.ts` `describe('photo fetching budget (B7)')`): `edge:` 2–4 fetches in flight, never more than four (RED: old code ran one at a time); `regression:` a hanging host stops at the budget and the catalog still finishes with all 16 rows (RED: old code made 16 calls); `regression:` out-of-order fetches land on their own rows. The spec's `@repo/ai` mock now exposes the real `createLimit` from its own file.
