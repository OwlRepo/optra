# Fix B8 — uploaded files keep their real UTF-8 name

Owner instruction 2026-10-02: continue through the bug list without waiting; pull the owner in only when a decision is needed.

- Classification: BUG_FIX · Standard (upload services, one shared HTTP helper, one web helper; no schema, queue or auth change) · Procurement + Vendor Catalog. Contract areas: API — the stored `name` of a new upload is the real name; download `Content-Disposition` gains `filename*` for a non-ASCII name (ASCII names unchanged). DB — none. Web — `filenameFromDisposition` reads `filename*` first.
- Root cause: multer 2.0.2 constructs busboy 1.6.0 with only `headers`, `limits` and `preservePath`; busboy's default `defParamCharset` is latin1, so the UTF-8 bytes of a browser filename were stored one character per byte (`faÃ§ture-æ¥æ¬.csv`).
- Second-order trap found in RCA: once the real name is stored, `attachmentDisposition` would put `日本` into a header and Node refuses characters above U+00FF (`ERR_INVALID_CHAR`), so the download would answer 500. The header fix ships in the same change.
- Fix: `decodeUploadFilename` (`common/http/upload-filename.ts`) re-reads the bytes as UTF-8. It leaves the name as received when it contains a character above U+00FF (busboy already decoded a `filename*`) or when the bytes are not UTF-8 (would only gain U+FFFD). It is applied in `ProcurementDocumentsService.upload` and `CatalogDocumentsService.upload` before the name reaches the row, the storage key and the extension check. `attachmentDisposition` sends `filename="<ASCII, others as _>"; filename*=UTF-8''<RFC 5987>` for a non-ASCII name; `filenameFromDisposition` prefers `filename*` and falls back when it cannot decode.
- Not changed (recorded): rows already stored as mojibake keep their names (a backfill is a data operation and can misfire on a name that was genuinely latin1); dataset and knowledge-base uploads (disabled surfaces) are not routed through the helper.
